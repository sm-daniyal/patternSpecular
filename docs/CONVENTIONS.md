# Conventions

Engineering conventions for Pattern Specular. Language-level code style lives in [CODE_STYLE.md](CODE_STYLE.md); this file is about *how we work*, not how we write code.

The project shape these assume: a Python/FastAPI backend with a LangGraph-orchestrated analysis engine calling the Google Gemini API via `google-genai` and `instructor`, a React + TypeScript frontend, and Neon Serverless PostgreSQL 16 as the production database. All code lives on `D:\pattern-specular\`; no operations on `C:`.

## Folder structure

Three concerns at the root: `backend/`, `frontend/`, `docs/`. Never mix.

Backend code is one installable package, `pattern_specular`, under `backend/src/` (a standard src-layout). Inside `backend/src/pattern_specular/`, separated by what code is *for*, not by file type:

- `api/` — FastAPI routers and request/response models. Thin.
- `engine/` — the seven-stage analysis pipeline and LangGraph orchestrator. Stage naming follows the [design spec](DESIGN_SPEC.md): intelligent components are *Agents*, deterministic components are *Modules*.
- `services/` — business logic callable from API handlers, jobs, and tests alike.
- `models/` — SQLAlchemy ORM models (17 models).
- `db/` — engine/session setup, Alembic migrations, raw queries if any.
- `jobs/` — entrypoints for on-demand work (demo seeding, dictionary growth review).
- `core/` — config, typed exceptions, logging setup.

Tests live in `backend/tests/`, a parallel tree mirroring the package's purpose folders (e.g. `pattern_specular/api/health.py` → `tests/api/test_health.py`). Create folders when there is code to put in them, not before.

## Dependencies and tooling

- **Python:** 3.12, managed with `pip` and a standard `venv`. Deps declared in `backend/pyproject.toml`.
- **Frontend:** `npm`; `frontend/package-lock.json` is committed.
- **Python lint/format:** `ruff` for both lint and format.
- **Python types:** `mypy --strict` against `backend/src/`.
- **Frontend lint:** `eslint`.
- **CI:** GitHub Actions runs lint, type-check, and tests on every PR. CI must pass before merge.

## Database, ORM, migrations

- **Database:** Neon Serverless PostgreSQL 16, cloud-hosted. SSL mode required; pooled connections. `DATABASE_URL` is the only connection surface — never hardcode credentials.
- **ORM:** SQLAlchemy 2.0 typed declarative API. Pydantic models are separate from ORM models; never use one for both roles.
- **Migrations:** Alembic, one revision per schema change. Autogenerated revisions are read and edited before committing. The migration history — not the model classes — is the schema source of truth. Current head: `0020_india_region_lexicon`.
- **DB-dependent tests:** tests marked `@pytest.mark.db` require a live PostgreSQL container. They run in CI against a PostgreSQL 16 service container and are safely skipped in offline environments. Unit tests are in-memory and never require the database.
- **Storage medium:** document text, flags, dismissals, agent outputs, and lexicon entries are stored relationally in Neon PostgreSQL — they are short-form and queryable. There is no blob storage in the current implementation.

## Testing

- `pytest` for Python (240 tests, 317 skipped, 0 failed); `vitest` for the frontend (251 tests, 0 failed).
- Tests mirror the `src/` layout. One behaviour per test.
- **Mock all Google API calls in unit tests.** Deterministic fixtures for Contextual Pass, Judge, and Recommendations outputs. Tests never hit the live Gemini API.
- **Gold set.** A small labelled set of documents (JDs, feedback, writeups) with known-correct flags. Engine calibration — precision/recall per stage, agreement rate — is measured against it, not assumed. The gold set is also the demo's seed data.
- The deterministic stages (Dictionary Module, Adjudicator, Verdict, Suppression, fingerprinting logic) get thorough unit tests — they are cheap to test and carry the system's correctness guarantees.

## Logging

- Structured JSON via `structlog`. Never `print`.
- Every log line carries a correlation ID propagated through the request or engine run. Engine stages log entry and exit with the flag or document ID — the audit trail is a product feature, not just ops hygiene.
- `DEBUG` tracing, `INFO` normal flow, `WARNING` unexpected-but-recoverable, `ERROR` failures.

## Error handling

- Typed exceptions in `core/errors.py`, all subclassing one project base error.
- API routes catch at the handler boundary only; engine stages raise, the orchestrator decides whether a stage failure kills the run or degrades gracefully (e.g. LLM pass fails → dictionary flags still return to the manager).
- Never swallow exceptions silently.

## Git

- Conventional Commits: `feat:`, `fix:`, `chore:`, `docs:`, `refactor:`, `test:`, `ci:`.
- Subject ≤ 72 chars, imperative mood. Body explains *why* when not obvious.
- One concern per commit. Stage explicit paths; never `git add .` or `git add -A`.

## Pull requests

- Branch names: `feat/<short-description>`, `fix/<...>`, `chore/<...>`, `spike/<...>`.
- Every PR references its issue (`Closes #12`) and says what changed, why, and how to test. A screenshot for any UI change.
- Keep PRs small enough to review in one sitting — if a PR mixes two concerns, it should have been two PRs.
- CI must pass before merge. Squash on merge; `main` stays linear and protected.

## Project management

- GitHub Projects with issue tracking. Milestones track feature phases; issues track individual tasks.
- Board hygiene is part of finishing work: an issue is not done until its PR is merged and the card is closed.

## Secrets

- Never commit secrets, even temporarily. `.env` is gitignored; `.env.example` (template only) is committed.
- `backend/.env` carries `DATABASE_URL` (Neon connection string) and `GOOGLE_API_KEY`. Both exist only in `.env` locally and in CI secret stores — never in code, issues, or logs.
- Synthetic data only: no real corporate documents, real employee names, or real feedback ever enter this repo. Demo peer-feedback data is mocked by design.
